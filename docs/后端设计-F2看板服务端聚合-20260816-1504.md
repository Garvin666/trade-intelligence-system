# 后端设计：F2 看板服务端聚合（dashboard-data 瘦身）

> 依据：《建议报告（前端）14:49 版》F2（首屏/筛选性能）与《建议报告（后端）14:49 版》I1/F2（看板全量下发 55MB / 单接口 6.5s / 并发即超时）
> 时间：2026-08-16 15:04　|　范围：Python 3.12 后端（`src/api/services.py`、`src/api/app.py`、`tests/`）

## 1. 目标与非目标

### 目标
| 编号 | 内容 | 验收 |
|---|---|---|
| G1 | `GET /api/dashboard-data` 无筛选/部分筛选时只下发**图表序列**（聚合），不再下发 102,960 行 history + 178,200 行 forecast 全量 | payload 从 57.3MB → < 1MB（-98%+） |
| G2 | 聚合语义可读：history 按日期跨组合均值、forecast 按 (date, model) 均值 | 无筛选 history ≤ 104 行、forecast ≤ 180 行 |
| G3 | 保持响应字段名与行结构兼容，**前端零改动**（在线模式直接可读聚合序列） | TrendChart x 轴 104 点正常绘制 |
| G4 | 筛选接口带 `limit` 支持（透传 history/forecast） | `?limit=52` 生效 |
| G5 | 聚合结果可缓存、并发安全 | 无筛选响应（缓存后）< 0.5s，pytest 全绿 |

### 非目标
- **不改离线快照**：`output/dashboard-data.json`（55MB 文件）与 `window.__TRADE_INTEL_OFFLINE__` 离线模式保持原样（本地文件不占网络，前端 `filterDashboardData` 继续过滤）。
- **不改** `/api/history`、`/api/forecast` 独立端点语义（已带 limit）。
- **不做**前端图表多组合拆分/分组（超出 F2 范围）。
- **不改**四脑引擎、trade 决策等其余端点。

## 2. 现状与根因（实测/代码核对）

### 实测
- `services.dashboard_data({})`：**1.26s / 57.3 MB**（history 102,960 行 + forecast 178,200 行全量 JSON）；浏览器实测 6.5s；并发即超时（B5 已用 meta 绕过，但首屏性能问题未解）。
- 筛选 `category=pet&market=us&model=lightgbm_advanced`：0.584s（含 CSV 首读），104/90 行。

### 根因（前端消费核对，`frontend/src/`）
- `DashboardPage.tsx` → `TrendChart rows={data.history}`：只用 `date/sales_volume/search_index/export_value`，且**不按组合拆 series**，把全部行当一条序列画 → 无筛选时 x 轴 102,960 点（乱线），图表语义本就不可读。
- `ForecastChart history/forecast`：只用 `date/sales_volume` 与 `date/yhat/yhat_lower/yhat_upper`，同样不拆 series。
- `MetricsGrid`：仅取 history 中**最新日期的 sales_volume 均值**（`latestAvgSales`）——聚合后语义完全等价。
- `RecommendationTable`：只用 `data.recommendations`（后端已 top=20 排序）。
- 结论：**图表消费的是"序列"而非"行明细"**，服务端按日期聚合是正确且无损的降载手段。

## 3. 实现决策

| 决策 | 方案 | 理由 |
|---|---|---|
| D1 history 聚合 | 新增 `_dashboard_history_series(filters, limit)`：`category` 与 `market` **都给定** → 返回筛选后的真实序列（104 行/组合）；否则对筛选后帧按 `date` 分组 `mean()`（保留全部数值列，聚合行补空组合字段），按 date 排序，可选 `limit`（**tail 取最近 N 期**） | 双筛选=真实组合曲线（现状正确）；部分/无筛选=跨组合均值曲线（修复乱线 + 降载 99.9%） |
| D2 forecast 聚合 | 新增 `_dashboard_forecast_series(filters, limit)`：双筛选 → 原始筛选行；否则按 `(date, model)` 分组均值（保留 date/model/yhat/yhat_lower/yhat_upper）；`model` 筛选恒生效 | 无筛选 178,200 → ≤ 180 行（2 模型 × 90 天） |
| D3 接入点 | `dashboard_data()` 内 `history`/`forecast` 字段改用上述系列函数；`recommendations`（top20）、`metrics`、`summary`、`trade_report`、`policy_events`、`data_status` 等小数据不变；`meta=1` 分支不变 | 响应结构零破坏 |
| D4 limit 透传 | `GET /api/dashboard-data` 增加可选 `limit: int` 查询参数 → 透传系列函数 | 满足"筛选接口带 limit/分页" |
| D5 缓存与并发 | 聚合结果包 `_cache_get`（TTL 15s，与 history()/forecast() 同机制） | 并发请求共享聚合结果，消除重复计算 |

## 5. 验收标准

- [ ] `services.dashboard_data({})` payload < 1MB（57.3MB → 目标 < 0.5MB），缓存后耗时 < 0.5s。
- [ ] 无筛选 `history` ≤ 104 行、`forecast` ≤ 180 行；行结构含前端所需字段（date/sales_volume/search_index/export_value、yhat/yhat_lower/yhat_upper/model）。
- [ ] `category+market` 双筛选返回真实序列（104 / 90 行，model 筛选生效）。
- [ ] `?limit=52` 后 history 恰 52 行。
- [ ] `meta=1` 轻量元信息行为不变。
- [ ] `pytest tests -q` 全量通过（383 项基线 + 新增）。
- [ ] 前端在线模式无需改动，DashboardPage 图表正常渲染（本地起后端 + 页面自检）。

## 6. 风险

- 无筛选时图表语义从"990 组合叠画乱线"变为"跨组合均值曲线"：属修复而非回归，离线模式保持原语义不受影响。
- 聚合均值对 `bestseller_rank` 等非均值语义列不精确：图表未消费这些列，仅保留兼容；如需精确聚合可后续按列选 aggfunc。
- limit 仅作用于 history/forecast 序列，不作用于 recommendations（其自身 top=20）。
