## 三、阻断级问题（本轮实测）

### B4（新增·最高优先）. 四脑分析触发原生访问冲突 → 整个后端进程崩溃（实测复现）

- **触发过程（实测）**：14:24 在 8000 端口 `/app/workbench` 点击"开始四脑分析"后，界面出现 `Failed to fetch`；探测 8000 端口**无进程监听**。
- **崩溃证据**：Windows 应用程序日志显示 `python.exe`（`C:\Users\26717\anaconda3\python.exe`）在 14:23-14:26 多次 APPCRASH，`Exception code: 0xc0000005`，崩溃模块 `MSVCP140.dll`（offset 0x13080）与 `python312.dll`（offset 0x124761）；同一时段 `chrome-headless-shell.exe` 亦崩溃一次。
- **根因线索**：`tests/` 9 处 skip 注释**早已写明**"四脑图表在部分 Windows 环境触发原生访问冲突"——已知缺陷只做了"跳过测试"，未隔离/守护真实运行路径。`src/four_brain/engine.py::build_charts`（1008-1079 行）本身是纯 Python dict 构造，崩溃源更可能在图表后续序列化/渲染或重负载并发（55MB dashboard-data + 66×15 热力图矩阵）下的 pandas/native 层。
- **影响**：演示现场在四脑工作台点一次分析，整个后端（REST + MCP + 前端静态托管）一起挂；后端无自动重启/守护，需手动拉起。**全系统最高演示风险。**
- **修复方向**：
  1. 短期止血：四脑图表生成改惰性/降级（`output_charts` 默认空、按需请求），或四脑分析放独立子进程（`ProcessPoolExecutor`）隔离崩溃；
  2. 根治：GitHub Actions（Linux）全量跑四脑用例 + Windows 逐步骤定位图表序列化，修复后**移除全部 9 处 skip**；
  3. 后端加进程守护（看门狗自动拉起 + 前端可感知降级提示，替代裸 `Failed to fetch`）。

### B5（新增·重要级中实测失败）. `/api/check` 与页面自检结果矛盾：dashboard-data 超时

- **实测**：API 直调 `/api/check` → `ok=31 warn=1 fail=0`；系统控制台"环境自检"页签内 → `ok=30 warn=1 fail=1`，fail 项"看板聚合数据：请求失败 timed out（5340ms）"。
- **原因**：`/api/dashboard-data` 单次 6.5s（55MB 全量 JSON），页面并行检查时超时。同一检查两入口、两结果，评委两边都点即见矛盾。
- **修复方向**：自检的 dashboard-data 检查改轻量版（查 `output/dashboard-data.json` 存在/时间戳，或服务端预聚合），或为检查专用 15s 超时；长期按 I1/F2 做服务端聚合。
