## 二、阻断级问题（本轮实测，答辩前优先处理）

### B4（新增·本轮最高优先）. 四脑分析触发原生访问冲突 → 整个后端进程崩溃（实测复现）

- **触发过程（实测）**：14:24 在 8000 端口的 `/app/workbench` 点击"开始四脑分析"后，界面出现 `Failed to fetch`；随后探测 8000 端口**无进程监听**。
- **崩溃证据**：Windows 应用程序日志显示 `python.exe` 在 14:23-14:26 多次 APPCRASH，`Exception code: 0xc0000005`（访问冲突），崩溃模块 `MSVCP140.dll`（offset 0x13080）与 `python312.dll`（offset 0x124761），均为 `C:\Users\26717\anaconda3\python.exe`；同一时段 `chrome-headless-shell.exe` 也崩溃一次。
- **根因线索**：`tests/test_api.py:417,432,455,492,508,524` 与 `test_search_api.py` 的 skip 注释**早就写明**"四脑图表在部分 Windows 环境触发原生访问冲突，Windows 下跳过"——即已知缺陷，但只做了"跳过测试"，**没有隔离或守护真实运行路径**。`src/four_brain/engine.py` 的 `build_charts`（1008-1079 行）本身是纯 Python dict 构造，崩溃源更可能在图表后续序列化/渲染或并发重负载（`dashboard-data` 55MB + 四脑热力图 66×15 全量矩阵）下的 pandas/native 层。
- **影响**：演示现场只要在四脑工作台点一次分析，**整个后端（含 REST/MCP/前端静态托管）一起挂**，页面全部 `Failed to fetch`；后端**无自动重启/守护**，需手动重启。这是全系统最高的演示风险。
- **修复方向（按成本排序）**：
  1. 短期止血：把四脑分析的图表生成改为**惰性/降级**（`output_charts` 默认空、页面按需请求，或图表数据量裁剪），或把四脑分析放到独立子进程（`multiprocessing`/`ProcessPoolExecutor`）隔离崩溃；
  2. 定位根因：在 Linux CI（GitHub Actions 已配）跑完整四脑用例 + Windows 上逐个排除图表序列化步骤，修复后**移除全部 9 处 skip**；
  3. 后端加进程守护：`run_api.py` 外层包一层 supervisor/看门狗，崩溃自动拉起，并向前端暴露可感知的降级提示（而不是裸 `Failed to fetch`）。

### B5（新增·重要级中实测失败）. 系统自检接口与页面结果不一致：dashboard-data 超时

- **实测**：API 直调 `/api/check` → `ok=31 warn=1 fail=0`；但系统控制台"环境自检"页签内跑出的结果 → `ok=30 warn=1 fail=1`，fail 项为"看板聚合数据：请求失败 timed out（5340ms）"。
- **原因**：`/api/dashboard-data` 单次 6.5s（55MB 全量 JSON），在页面并行发起多个接口检查时超时。同一个检查，两种入口、两个结果——评委若两边都点会看到矛盾。
- **修复方向**：`/api/check` 的 dashboard-data 检查改走**轻量版**（如只查 `output/dashboard-data.json` 的存在与时间戳，或服务端预计算聚合），或为检查设置专用 15s 超时；长期按 I1 做服务端聚合。
